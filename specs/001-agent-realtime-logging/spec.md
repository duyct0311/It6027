## User Scenarios & Testing *(mandatory)*

### User Story 1 - Multi-Agent Real-time Log Ingestion via WebSocket (Priority: P1)

As an Agent running on a client machine, I want to establish a persistent WebSocket connection to the Web Server and stream malware scan logs in real time, so that the server immediately receives and records detection events without polling latency.

**Why this priority**: Core foundation of the system. Without real-time log ingestion over WebSocket, malware detections cannot be centrally gathered or alerted immediately.

**Independent Test**: Can be tested independently by launching simulated Agent scripts that connect via WebSocket, sending sample JSON log payloads, and verifying the server parses, validates, and persists each entry into the database tagged by AgentID.

**Acceptance Scenarios**:

1. **Given** an active Agent connected via WebSocket, **When** the Agent sends a scan log payload matching the standard format (`AgentID`, `Module`, `Name`, `Path`, `ScanType`, `Severity`, `Status`, `Time`, `version`), **Then** the server acknowledges the payload, saves it to persistent storage under the specified `AgentID`, and broadcasts the event to active Admin dashboard subscribers within 500ms.
2. **Given** multiple Agents (e.g., Agent A and Agent B) connected simultaneously, **When** both Agents stream scan logs at the same time, **Then** the server maintains separate, non-interfering log streams and stores each log associated strictly with its respective `AgentID`.
3. **Given** an Agent sending a payload with missing mandatory fields or invalid types, **When** the payload arrives at the server, **Then** the server logs a schema validation warning, isolates the invalid payload in a quarantine log table, and keeps the WebSocket connection open for subsequent valid messages.

---

### User Story 2 - Dedicated Single Admin Web Authentication (Priority: P1)

As the System Administrator, I want to authenticate into the Web Server dashboard using dedicated Admin credentials, so that only authorized personnel can access system logs, agent management, and server capabilities.

**Why this priority**: Critical security requirement defined in the project constitution. Unauthorized access to malware management features presents a severe security risk.

**Independent Test**: Can be tested independently by submitting correct and incorrect credentials at `/api/auth/login` and verifying access token generation, route protection, and rejection of unauthenticated API calls.

**Acceptance Scenarios**:

1. **Given** the Admin user on the login screen, **When** valid Admin credentials (username & password) are submitted, **Then** the server returns a secure JWT token, establishing an authenticated session with full administrative privileges.
2. **Given** an unauthenticated user or an invalid credential submission, **When** access to protected Web Server routes or APIs is attempted, **Then** the system rejects access with an HTTP 401 Unauthorized status and redirects the user to the login screen.
3. **Given** an active Admin session, **When** the Admin clicks Logout or the token expires, **Then** the session is invalidated immediately, clearing stored tokens and revoking access.

---

### User Story 3 - Multi-Agent Log Management & Granular Filtering (Priority: P2)

As the Administrator, I want to view, group, and filter scan logs by Agent ID, Severity, Scan Type, Status, Module, or File Path on the web dashboard, so that I can analyze security threats efficiently across all managed endpoints.

**Why this priority**: Essential for operational analysis. Administrators need clear visibility into which endpoints are infected and what actions were taken.

**Independent Test**: Can be tested independently by populating the database with logs from multiple Agents and applying various filter criteria in the UI to confirm accurate dataset reduction.

**Acceptance Scenarios**:

1. **Given** an authenticated Admin on the log dashboard, **When** the Admin selects a specific `AgentID`, **Then** the UI displays only the scan logs generated by that specific Agent.
2. **Given** an aggregated log view, **When** the Admin filters by `Severity = High` and `Status = DETECTED_ONLY`, **Then** the list instantly updates to show only matching high-severity alerts requiring intervention.
3. **Given** a large history of logs, **When** the Admin enters a keyword (e.g., `dll_test.exe` or `C:\Users`), **Then** matching logs are highlighted and filtered across file paths and threat names.

---

### User Story 4 - Agent Connection Monitoring & Dashboard Summary (Priority: P3)

As the Administrator, I want to monitor active Agent connection status (Online/Offline) and view aggregate threat statistics, so that I have complete situational awareness of endpoint health.

**Why this priority**: Provides high-level operational visibility and system health monitoring.

**Independent Test**: Can be tested independently by connecting/disconnecting agents and verifying real-time status badge updates on the dashboard summary card.

**Acceptance Scenarios**:

1. **Given** an Agent establishing or closing a WebSocket session, **When** the connection status changes, **Then** the server updates the Agent's status (`Online` vs `Offline`) and last-seen timestamp on the Admin dashboard in real time.
2. **Given** incoming scan logs over time, **When** the Admin views the dashboard summary, **Then** key metrics (Total Agents, Active Detections count, Critical Threats, Total Scans today) reflect up-to-date totals.

---

### Edge Cases

- **WebSocket Reconnection & Buffer**: What happens if an Agent loses internet connectivity mid-scan? The Agent MUST buffer unsent log payloads locally and flush buffered logs sequentially upon WebSocket reconnection without creating duplicate log records.
- **Log Burst Throttling**: What happens if an infected Agent generates 5,000 detection logs in 10 seconds? The server WebSocket handler MUST ingest messages into an async processing queue to prevent event-loop blocking or database lockouts.
- **Malformed Timezone / Offset Handling**: What happens if an Agent transmits timestamps with unusual timezone offsets (e.g., `+06:59`)? The server MUST parse ISO 8601 strings accurately, convert timestamps to UTC for storage, while preserving original local time representation for display.
- **Single Admin Lockout Safeguard**: What happens if multiple login attempts fail consecutively? The server MUST enforce rate-limiting on login endpoints to prevent brute-force attacks against the single Admin account.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Server MUST expose a dedicated WebSocket communication endpoint (`/ws/agent`) dedicated to receiving agent telemetry and streaming scan logs in real time.
- **FR-002**: Server MUST authenticate connecting Agents during WebSocket handshake using a pre-shared Agent token or registered `AgentID`.
- **FR-003**: Server MUST validate incoming JSON log payloads against the strict specification schema:
  - `AgentID` (String/UUID, required)
  - `Module` (String, required, e.g., `"AI"`, `"YARA"`, `"Hash"`)
  - `Name` (String, required threat/rule identifier)
  - `Path` (String, required file/folder path on agent host)
  - `ScanType` (String, required, e.g., `"Realtime Protection"`, `"Manual Scan"`)
  - `Severity` (String, required: `"Low"`, `"Medium"`, `"High"`, `"Critical"`)
  - `Status` (String, required: `"DETECTED_ONLY"`, `"QUARANTINED"`, `"DELETED"`)
  - `Time` (ISO 8601 Timestamp with timezone offset, required)
  - `version` (String, required protocol version, e.g., `"1.0"`)
- **FR-004**: Server MUST persist validated scan log records into a relational database, linking each log immutably to the corresponding `AgentID`.
- **FR-005**: Server MUST push incoming log events via WebSockets to authenticated Admin web dashboard sessions in real time (<500ms delay).
- **FR-006**: System MUST enforce single Admin authentication (`Role = Admin`) for web dashboard access.
- **FR-007**: Server MUST protect all Web REST APIs and dashboard WebSocket channels using JWT tokens; unauthenticated requests MUST receive HTTP 401 Unauthorized.
- **FR-008**: Web dashboard MUST allow Admin to view logs aggregated system-wide or grouped by individual `AgentID`.
- **FR-009**: Web dashboard MUST support multi-criterion filtering by `AgentID`, `Severity`, `ScanType`, `Status`, `Module`, `Date/Time Range`, and free-text search on file `Path` or malware `Name`.
- **FR-010**: Server MUST track and expose real-time Agent connection state (`Online` / `Offline`) and `LastSeen` timestamp.
- **FR-011**: Server MUST quarantine malformed or unparseable WebSocket log payloads into an audit error log without closing the active WebSocket connection.
- **FR-012**: Web UI MUST render high-volume log updates smoothly without UI lag, pagination freezes, or memory leaks.

### Key Entities

- **Agent**: Represents a managed client endpoint (`AgentID`, `Hostname`, `IPAddress`, `Status` [Online/Offline], `LastSeenTimestamp`, `AgentVersion`, `CreatedAt`).
- **ScanLog**: Represents an individual file scan result received from an Agent (`LogID`, `AgentID`, `Module`, `ThreatName`, `FilePath`, `ScanType`, `Severity`, `Status`, `EventTimestamp`, `PayloadVersion`, `ReceivedAt`).
- **AdminUser**: Represents the single administrative user account (`UserID`, `Username`, `PasswordHash`, `Role` = `"Admin"`, `LastLoginTimestamp`, `CreatedAt`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Scan logs streamed by an Agent arrive and display on the Admin dashboard in under 500 milliseconds via WebSocket.
- **SC-002**: System ingests up to 1,000 log events per second across multiple concurrent Agent connections without dropping messages or exceeding 50% CPU usage.
- **SC-003**: Admin authentication completes and renders the web dashboard in under 1.5 seconds.
- **SC-004**: Admin can filter, sort, and search through 100,000 historical scan logs with query results returning in under 2 seconds.
- **SC-005**: 100% of unauthenticated API or WebSocket connection attempts to protected resources are successfully blocked with HTTP 401/403 errors.

## Assumptions

- Single Admin credential model is sufficient for phase 1; multi-tenant or role-based user management can build on this single-admin foundation in future phases.
- Agents maintain local clock synchronization (NTP) to ensure accurate log timestamps.
- WebSockets use standard WSS (TLS encrypted) in staging/production and WS in local development.
